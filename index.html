Demand forecasting & review priorities

Completed

Which forecasts can a planner trust, and which five items deserve a review each week?

  • 21%more accurate than the week-over-week baseline
  • 89%of actual sales inside the 90% forecast ranges
  • 5×more forecast error caught than random picks
Read the case study View code on GitHub
  1. Problem

    A planner can’t review every forecast every week. Which forecasts are reliable, and which five products deserve their attention?

  2. Approach

    Compare seasonal-naive, ETS and LightGBM in a 60-origin weekly rolling backtest. Every forecast uses only data up to its forecast date, and the final 28 days stay sealed until all choices are frozen.

  3. Build

    A Python and SQL pipeline from raw sales to a weekly review list, checked in DuckDB and presented in a 10-page Power BI dashboard. Hover or tap the steps below.

  4. Result

    21% lower error than the baseline, honest 90% ranges (89% coverage), and a 5-item review list that caught 5× more error than random. Recommendation: LightGBM, with ETS as the fallback.

  1. Problem

    J&J buys from ~29,000 suppliers. Most hold little spend but cost the same to onboard, audit and pay. Which ones can go without adding supply risk?

  2. Approach

    Four questions, one method each: where the spend sits (Pareto / ABC in SQL), how to treat each category (Kraljic), which suppliers stay (ML duplicate matching, scorecard and rules R1–R8), and what it is worth (measured price gap plus scenarios).

  3. Build

    A Python and SQL pipeline that traces every raw row to a decision, an Excel model with live formulas, a 4-page Power BI dashboard, and MOU, MSA and supply-agreement templates for the kept suppliers.

  4. Result

    73% fewer supplier records, suppliers per category halved. The price-gap test corrected my first estimate: savings exist only in competitive categories, so the plan needs a 1.15% re-tender saving to clear $300M a year.

Launch go/no-go: software meets supply

Completed

Will each TV launch ship on time when a supplier slips?

  • 16launches recalculated live when you delay a shipment
  • 26 daysof testing delay traced back to one late part
  • 32automated tests behind every number
Read the case study Try the live demo View code on GitHub
  1. Problem

    Software readiness and supply live in different tools. At Samsung, “software isn’t ready” often really meant “we didn’t have boards to test on”, and the part shortage behind it sat in another team’s spreadsheet.

  2. Approach

    One verdict per launch. Software side: when testing can start and a ready-date range per chipset. Supply side: parts handed out in need-date order, each unit only once. The launch gets the worse of the two, with reasons from both.

  3. Build

    A plain JavaScript engine shared by the app and 32 automated tests: launch, software and supply views, a what-if lab, three scenarios, and a recovery workflow where a person approves or rejects each option.

  4. Result

    In the USB delay scenario, testing moves from 12 Nov to 8 Dec and software lands 8–15 Jan against an 11 Jan cutoff. Re-pegging 20 controllers from another program’s order restores the launch.

How I work

The same five habits, whether it was a TV launch, a bank’s servers or a forecast.

  1. 01

    Understand the deadline and who depends on it

    Every TV launch I worked on had a fixed date, and product, QA and design were waiting on it. I start by learning the date and who needs the answer.

  2. 02

    Find what’s actually blocking it

    Usually it’s a few things, not everything. At Samsung we ranked fixes by customer impact so the important ones went first.

  3. 03

    Fix it in the data, not by guessing

    At DXC, recurring-incident patterns decided which legacy servers to retire first, not opinions.

  4. 04

    Check the numbers twice

    In the Walmart study every result was recomputed in SQL, and every dashboard figure reconciled against the code: 351 of 351 checks.

  5. 05

    Track it until it’s done

    Every release I owned shipped on schedule. I follow the work to the date, not just to the handoff.
